研究前沿：推理引擎正在往哪走

前面的章节讲的都是"已经定型的机制"。这一章换一个角度：2025–2026 年，做推理系统的人正在解决什么问题、用什么办法、拿到了多大的数字、还剩什么没解决。它更像一张地图而不是教程——读完之后，你应该能判断一篇新论文在打哪一场仗，也能看出哪些"优化"其实是在把瓶颈换个地方。

为什么重心从 kernel 移到了数据移动

2022–2024 年，推理性能的提升主要来自把单个算子写快：FlashAttention 把注意力的访存从平方降到线性、PagedAttention 把显存碎片压掉、连续批处理把 GPU 的空闲填满。这些优化现在已经被吃到极限——主流的三个生产引擎（vLLM、SGLang、TensorRT-LLM）在这些点上的差距通常只剩个位数百分比。

而 roofline 那笔账没有变：一次 decode 要把 16 GB 权重从显存读一遍，算力只用掉 2%–3%。把 kernel 写快解决不了"读得多"。于是 2025 年之后的研究集中在四个动作上：

动作典型手段收益量级成熟度
搬得少KV 量化、稀疏注意力、GQA/MLA、线性注意力2–50×已进模型结构
搬得快NVLink、RDMA、分层存储、异步拷贝4–30×已产品化
搬得巧PD 分离、前缀缓存、跨实例共享、按会话调度1.5–6×产品化中
少搬一次投机解码、MTP、批内复用1.5–3×已进默认配置

这张表也是下面八条主线的索引：每一条都在打其中一行。

主线一：PD 分离，从"拆开"到"按 SLO 自动配比"

预填充吃算力、解码吃带宽，放在同一张卡上必然有一半资源闲着。2024 年的 DistServe、Splitwise 证明了"拆开"有效，2025 年之后的问题变成了三件：拆开之后比例怎么定、KV 怎么搬、异构硬件上怎么搬。

  • Mooncake（FAST'25 最佳论文）把整台服务改造成以 KVCache 为中心：prefill 集群与 decode 集群分离，同时把推理集群里闲置的 CPU、DRAM、SSD、NIC 组成一个独立的 KV 缓存池，再由全局缓存与调度器在 SLO 约束下最大化吞吐。真实流量下有效请求处理能力提升 59%–498%，已在数千节点上每天处理 1000 亿 token。来源
  • Dynamo 与 llm-d 把这件事产品化：Planner Profiler 先测出本机型的性能曲线，SLA Planner 再按目标 SLO 自动匹配 prefill:decode 的实例比例；KV 通过 NIXL 在 RDMA 上搬；多模态进一步拆成 EPD（encode–prefill–decode）三段。Dynamo 会议、机制说明
  • 异构 PD 是 2026 年的新方向：AsymFlow 让 CPU 承担预填充/解码分离后的部分工作，其 CPU 侧 decode 注意力算子快 2 倍（ICPP'26）；PiKV-Serve 面向边缘-云链路，把 KV 按层流水线迁移、与计算重叠（IEEE）。

还没解决：KV 传输的尾延迟（一次 1.28 GB 的跨节点搬运就是几十毫秒，见第 11 章的分层表）、prefill:decode 比例对负载突变不鲁棒、跨数据中心基本不可行。

主线二：KV cache 从"副产品"变成"一等存储"

这是过去两年变化最大的一条。核心认识是：KV 是可以被寻址、复用、分层、跨实例共享的对象，而不是某个请求的私有中间变量。

  • LMCache 把卸载做成独立服务：在 Dynamo 里以 DaemonSet 跑，通过跨 Pod CUDA IPC 与 worker 共享张量（文档）；2026 年又做了多节点 P2P CPU 内存共享，专门解决"多实例各攒各的缓存"——四个实例时缓存命中率会掉到 1/4（博客）。
  • 全局 KV 感知调度：Axon（SIGOPS ATC'26）把"上下文在哪台机器上"变成调度变量——会话级的上下文可以在 GPU 常驻缓存与 CPU 内存之间迁移，优先走 PCIe 恢复、必要时才做 GPU-GPU 迁移，已实现在 vLLM 之上，用生产 agent 轨迹在 4 台 A100 上评测（论文）。
  • 反向的声音：vAttention 认为分页本身是性能负担——它用操作系统式虚拟内存加 CUDA VMM 做"按需映射的连续 KV"，并引用实测：paged prefill kernel 比非分页慢约 42%，部分场景整体延迟高约 5%（论文）。这条线提醒：分页解决碎片，但把复杂度转嫁给了 kernel。

还没解决：缓存一致性（权重版本、LoRA、精度）、失效语义、跨租户的计时侧信道（第 11 章安全一节）、跨集群共享的可行性。

主线三：架构与系统的协同设计

模型结构正在为了服务成本而改变，这是 2025 年最值得注意的趋势。三例子：

  • DSA（DeepSeek Sparse Attention）：V3.2-Exp 用两级注意力——先由 lightning indexer 给全量缓存打分、每层保留 top-2048，再对这 2048 个 token 做稀疏注意力（技术说明）。
  • 瓶颈搬家：长上下文下 decode 的时间花在"每层扫一遍全量缓存"的索引器上，注意力每层都要等它。NeurIPS'26 的多层索引器论文进一步指出：相邻层选出的 token 高度重叠，因此索引器可以跨层共享（论文）。
  • 线性与混合注意力（Qwen3-Next 的 Gated DeltaNet 层、Mamba/RWKV 类状态递推）：KV 不再随长度增长，但 decode 每步要读写固定大小的状态矩阵。按 3 层 GDN + 1 层全注意力的配置估算，GDN 的 decode 算术强度只有约 0.87 FLOP/B——瓶颈从"读 KV"变成"读写状态"。

还没解决：稀疏索引器自身的高效 kernel、混合架构的缓存语义（循环状态与 KV 并存）、训练与推理在稀疏模式上的一致性。

主线四：投机解码从论文走进默认配置

  • EAGLE-3 不再训练独立草稿模型，而是在目标模型内部层挂一个只有 2%–5% 大小的草稿头，在特征级与词元级同时预测；Google Vertex AI 用 SGLang 大规模部署，解码提速约 2–3 倍（博客）。
  • MTP（多 token 预测）从 DeepSeek-V3 起成为新模型的标配头，推理引擎把它当"内置投机"。
  • 研究点转到了交互项：接受率随 batch 增大而衰减、被拒绝的草稿 token 不能写进 KV 缓存（否则下一次命中就错，见第 11 章前缀缓存一节）、与结构化输出/约束解码的先后顺序。

主线五：MoE 与大规模并行

  • wide EP：DeepSeek 的 large-scale EP、DeepEP 通信库把专家并行推到几十卡；TensorRT-LLM 在 GB200 上做了 EP32 的实测，在线 EPLB 周期性重排专家放置，配合专家副本把最热的 rank 打散（技术博客）。
  • 研究点：all-to-all 与注意力的重叠、路由负载偏斜、专家副本的收益与显存代价、EP 规模上去之后的故障恢复（FailSafe、ReviveMoE 一类工作）。

主线六：kernel、编译与精度

  • FlashAttention-4 是"算法与流水线协同设计"，针对 Blackwell 的非对称扩展（tcgen05、warp specialization、软硬件协同的 softmax 重缩放）。论文、CuTe DSL 实现
  • 手写 kernel 仍不可替代：CuTe DSL 让"只针对某代 GPU 的高性能库"变得可行，比如只支持 SM120 的 NVFP4 GEMM / MoE / paged attention 库，直接对接 vLLM 与 SGLang（b12x）。
  • 编译与自动调优的代价被正式对待：TensorRT-LLM 的一个改动显示，首次 prefill 要编译 42–59 个 Triton 变体、每 rank 约 31 秒；改成提前预编译后降到约 5 秒（PR）。
  • 研究点：JIT 冷启动、CUDA graph 与动态形状的冲突、FP8/FP4 的 scale 布局、注意力后端与批次形状的兼容性。

主线七：长上下文与 agent 负载

  • Decode Context Parallelism（DCP）：decode 阶段把 KV 按序列切到多卡，用更多 GPU 换更长上下文与更大并发；vLLM 在 2026 年专门写了博客讲它在长上下文 agent 场景下的收益（博客）。
  • 负载形态变了：长思维链让推理从"算力受限"转向"容量受限"——KV 随思考长度线性增长，系统刻画显示 8B 到 671B 的最优并行策略都因此改变（IEEE 2026）；KV 剪枝开始针对推理负载做层与时间自适应（Lethe，AAAI'26）。
  • 容量分层：短上下文走低延迟实例、中长上下文走平衡配置、超长上下文走专用池（实践综述）。

主线八：调度、公平与可运维性

  • 体验公平：AAAI'26 的 Experiential Fairness 指出，按资源分配的公平性与用户感知的流式体验并不一致，提出以"体验"为目标的调度（论文）。
  • 故障与恢复：FailSafe 处理不规则 GPU 可用性下的张量并行；ReviveMoE 面向大规模 MoE 的快速恢复（概述见这份运维对照）。
  • 容量规划用模拟器：Vidur 只做一次 profiling，就能在 CPU 上模拟调度策略、投机解码与并行配置的端到端性能（工具）。

三个判断

一、重心从单个算子移到数据移动

单算子优化的空间已经吃尽，剩下的大头是"KV 放在哪、谁来搬、什么时候搬、按什么规则分给谁"。这也是为什么过去两年最亮眼的结果多来自系统论文而不是 kernel 论文。

二、模型与系统开始共同设计

DSA、MTP、混合线性注意力都是"为了服务成本而改结构"；反过来，引擎也在为这些结构定制 kernel（稀疏索引器、状态缓存、MLA 吸收）。两边不再是上下游，而是同一个设计问题的两半。

三、目标从吞吐变成延迟承诺、公平与成本

多租户、agent 长会话、推理模型的长时间思考，都在迫使调度器处理"尾延迟、缓存命中率、单位会话成本"，而不是只盯 tokens/s。可承诺的延迟正在成为比峰值吞吐更重要的指标。

反面提醒：没有免费的优化

本页出现过三次"瓶颈搬家"：稀疏把瓶颈搬到索引器，线性注意力搬到状态读写，PD 分离把瓶颈搬到 KV 传输。看到一个优化，先问它把成本挪到了哪里、那个地方会不会成为新的墙。

如果你要做研究：八个可验证的空白

  1. 多层索引器的选择一致性：相邻层重叠多少才算"可以共享"？需要的是可度量的选择相似度，以及共享之后的精度损失上界。
  2. 混合架构的缓存语义：GDN/Mamba 的循环状态与 KV 并存时，"前缀缓存"该怎么定义？状态的更新不是只追加，复用条件要重新推。
  3. 跨集群 KV 迁移的 SLO 可行性：在 50 ms 量级的广域链路上，什么规模的请求值得搬、什么规模不如重算？目前只有单机房数据。
  4. 投机 + 前缀缓存 + 约束解码的三方交互：三者对"哪些 token 合法"的判断顺序不同，组合起来的一致性还没有系统论证。
  5. 稀疏注意力的 prefill kernel：现有稀疏优化大多针对 decode；prefill 阶段块稀疏在张量核心上的利用率仍是开放问题。
  6. 会话级容量规划：agent 的 SLO 不是"每个请求多快"，而是"这个会话多久能推进完"，需要新的度量与调度目标。
  7. 联合基准：长上下文 + agent + 投机的组合负载缺一个公认基准，现有 benchmark 各自只覆盖一角。
  8. 共享缓存的安全：前缀缓存的计时侧信道已有攻击，但"可证明的防护 + 可接受的性能损失"还没有落地答案。

这一章的用法

把这张地图当目录：遇到新论文，先定位它打的是哪一行、把成本挪到了哪里；做选型时，先问自己的负载落在哪个区间（长上下文?agent?高并发短请求?），再挑对应主线的结论。本书前面所有章节给的数字都是"机制不变时的账"，这一章给的是"机制正在变的方向"——两者一起看，才不会把某一年的最优配置当成永恒答案。
