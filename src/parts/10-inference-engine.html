第十章 · 推理工程

推理引擎：把 FLOPs 变成毫秒

数学上，生成一个 token 就是一次前向传播。工程上，这次前向要真金白银地占显存、搬数据、排队等待。这一章讲一次请求从进 GPU 到吐出第一个字的全过程：为什么大模型解码不是算力瓶颈而是显存带宽瓶颈，以及行业为此积累下来的四类优化手段。KV cache 的细账（GQA/MLA、分页、前缀缓存、量化、淘汰）单独放在第 11 章，因为它是这一章里最贵、也最值得展开的一部分。

两个完全不同的阶段

一次对话的推理分成两段，它们的性能特征截然相反：

Prefill（预填充）

把你的整段输入一次性送进模型。T 个 token 并行计算，每个权重被用 T 次，GPU 的算力被吃满。这一阶段是计算密集的，耗时随输入长度线性增长，但吞吐很高。它决定了用户等待第一个字的时长。

Decode（解码）

每次只生成一个 token。一次前向只为 1 个位置服务，但要把整个模型的权重从显存读一遍。算力几乎闲着，全在等数据搬运。这一阶段是带宽密集的，也是用户感知到的"打字速度"。

这个差别带来一个不太直观的结论：单个用户解码时，GPU 的算力利用率只有百分之几——时间几乎全花在把权重从显存搬到计算单元上。下面把这一步算一遍。

两个延迟指标：TTFT 与 TPOT

服务端不看"算力利用率"，看两个延迟指标：

  • TTFT（Time To First Token）：从请求到第一个 token 出现，由 prefill 决定。输入 2000 token、prefill 吞吐 5000 token/s 时，TTFT ≈ 0.4 秒。
  • TPOT（Time Per Output Token）：之后每个 token 的间隔，由 decode 决定，也就是上面算出的 4.8 毫秒起步。TPOT 20ms 对应约 50 token/s 的"打字速度"。

这两个指标对应两种完全不同的优化：prefill 想提高算力利用率（更大 batch、更长 chunk、FlashAttention），decode 想减少每步搬运的字节（量化、GQA、更小的模型、投机解码）。把它们混为一谈，就会得出"换个更快的 GPU 就能让每个用户都快 3 倍"这种错误结论。

prefill 阶段：从一个请求进来到第一个 token

把引擎想象成一条流水线。一个 prefill 请求进来，管线要做九件事；任何一件做错，表现出来的都是 TTFT 变长，或者直接报错。

  1. 接入与分词　tokenize 成 \(T\) 个 id，校验 max_model_len 与上下文长度，分配请求 id、采样参数、停止条件。
  2. 前缀缓存查询　按块哈希去查已有的 KV 块（第 11 章）。命中的块直接挂到请求的 block table，只对未命中的后缀计算——命中 1800/2000，就等于少算 90% 的 prefill。
  3. 排队与预算　进入等待队列。调度器按本步的 token 预算（max_num_batched_tokens，常见 8192）决定这次算多少；\(T\) 超过预算就切成多块（chunked prefill），先算第一块。
  4. 分配 KV 块　按 \(\lceil T/16\rceil\) 个块申请（块大小 16 token，见第 11 章）。池里不够就排队，或者抢已经占着显存的请求。
  5. 组批与元数据　把多个请求的 prefill 拼成一个变长 batch，用四张表描述：query_start_loc（哪几行属于哪个请求）、seq_lens（各自长度）、block_tables（逻辑块到物理块）、slot_mapping（本步往哪写 KV）。
  6. 执行前向　\(M=T\) 的大 GEMM（QKV 投影、FFN）+ 分块因果注意力（第 13 章）；张量并行时每层两次 all-reduce。
  7. 只对最后一个位置采样　logits → 温度 / top-k / top-p / 约束掩码 → 抽出第一个 token。前面 \(T-1\) 个位置只贡献 KV，不产生输出——第 8 章算过为什么可以只取最后一行。
  8. 写 KV、更新状态　本步算出的 \(k,v\) 按 slot_mapping 写进物理块；seq_len += T，block table 追加。
  9. 流式返回　detokenize 第一个 token 推给客户端（这就是 TTFT 的终点），请求转入 running 队列交给 decode。

decode 阶段：每五毫秒重复一次的那九件事

decode 每一步只生成一个 token，却要重复同一套动作。它的九件事和 prefill 几乎一一对应，但每一件的成本结构完全相反。

  1. 取活跃请求　从 running 队列挑本步要算的 \(B\) 个请求。\(B\) 受两个东西限制：max_num_seqs，以及池里还有没有空余 KV 块。
  2. 分配新槽位　每个请求需要 1 个新 token 的槽位；最后一块满了就申请一个新的物理块，写进 block table。
  3. 组装元数据　block_tables、seq_lens、slot_mapping（每请求一项，指向本步要写的槽位）。
  4. 选图并重放　按 \((num\_tokens=B,\ num\_reqs=B)\) 挑最近的分档 CUDA graph 直接重放（第 13 章）；形状不在任何一档就退回 eager，那一小批请求会明显变慢。
  5. 执行前向　QKV 投影变成 \(B\) 行的瘦 GEMM/GEMV；注意力对每个请求读一遍 \(T\) 长度的 KV——这是整步的大头；FFN 同理。
  6. 采样　\(B\) 个位置各抽一个 token（温度、top-k、top-p）；投机解码在这一步校验草稿（第 14 章）。
  7. 写 KV、更新长度　把新 token 的 \(k,v\) 写进 slot_mapping 指定的槽位，seq_len += 1。
  8. 检查结束条件　遇到 EOS、stop 串、max_tokens 就释放该请求的 KV 块、把它移出队列并返回结果。
  9. 处理显存不足　池子满了就按策略抢占（第 12 章）：删掉某些请求的块、之后重算（RECOMPUTE），或换到 CPU（SWAP）。被抢占的请求会表现为"卡住一下"。

这张表解释了两个常见现象：单路 decode 只有 200 tok/s 左右（受带宽上限约束，与 GPU 算力无关）；而把 batch 拉到 32，总吞吐能到 4000+ tok/s——但单个用户感受到的间隔仍然是 7.3 ms/token。这就是第 12 章里"吞吐与延迟是两个目标"的来源。

混合批次：引擎怎么同时做这两件事

真实服务里两者永远同时在跑：有人在等第一个字（prefill），有人在等下一个字（decode）。引擎不会为它们开两个进程，而是把两类请求拼进同一个批次。做法和代价都很具体：

  • 预算切分　每一步的 token 预算先分给 decode（每个请求 1 个 token），剩下的才给 prefill 的块。这就是第 12 章那条"先 decode、后 prefill"的调度规则。
  • 块的粒度决定抖动　chunk 越大，TTFT 越低，但一步里塞的 prefill token 越多，正在解码的用户那一拍就被拖长。按 8B 单卡约 15000 tok/s 的 prefill 吞吐估：chunk 8192 ≈ 546 ms 的 ITL 毛刺，2048 ≈ 137 ms，这也是生产上多半取 2048–8192 的原因。
  • kernel 要能吃"不统一的 batch"　同一批里有的 query 长度是 1（decode）、有的是几千（prefill chunk），注意力 kernel 必须支持这种混合形状；支持不好的后端会被拆成两个 kernel，两次启动、两倍开销（第 13 章的能力枚举）。
  • CUDA graph 不友好　混合批次的形状组合太多，很难逐个捕获；很多引擎在混合批时回落到 eager，或者只对纯 decode 批启用图——这也是"纯 decode 批"在某些引擎里反而更快的隐藏原因。

把这一节和上面两张表合起来看，prefill/decode 的"原理"其实就一句话：同一个模型、同一套权重、两种完全不同的算术形状。引擎的所有动作——排队、切块、分块、组批、选图、抢占——都是在给这两种形状找各自的资源。

roofline：算术强度决定瓶颈

一个计算任务到底卡在算力还是带宽，可以用一个比值判断：算术强度（arithmetic intensity），即每搬运 1 字节数据做了多少次浮点运算。

\[ I = \frac{\text{FLOPs}}{\text{Bytes}} \qquad \text{可达性能} = \min\big(\text{峰值算力},\ I \times \text{带宽}\big) \] 10.1

把峰值算力和带宽的比值叫"脊点"（ridge point）。H100 的 FP16 峰值 990 TFLOPS、HBM 带宽 3.35TB/s，脊点 ≈ 295 FLOP/字节。算术强度低于它的任务带宽受限（曲线贴着带宽那条斜线），高于它的任务算力受限（曲线被算力上限压平）。

FlashAttention：注意力分块算

标准注意力要把 \(T\times T\) 的分数矩阵写回显存再读出来做 softmax。T=8192 时，这个矩阵有 6700 万个元素，每层、每个头都要读写一遍，显存带宽全耗在搬运中间结果上——而 prefill 恰恰是算力密集的，带宽被中间矩阵吃掉，性价比很差。更糟的是 \(O(T^2)\) 的显存直接爆掉。

FlashAttention 的做法是分块 + 在线 softmax：把 K、V 切成能放进 SRAM 的小块，逐块算分数、逐块更新 softmax 的分子分母和当前输出。全程只保留一个"运行中的最大值和归一化因子"，\(T\times T\) 矩阵从不落地。

\[ m^{(j)} = \max\big(m^{(j-1)},\, \max_i z_i\big),\qquad \ell^{(j)} = e^{m^{(j-1)}-m^{(j)}}\ell^{(j-1)} + \sum_i e^{z_i-m^{(j)}} \] 10.2

这个公式是 FlashAttention 的核心：最大值更新后，旧的累加和要按新的最大值重新缩放。数学上和一次性 softmax 完全等价，只是把"先全部算完再归一化"改成了"边算边归一化"。注意它是精确的同一计算，不是近似。

量化：把字节数降下来

既然瓶颈是"读权重"，那把权重存小一点就直接提速。量化把浮点数换成低精度整数：

格式每参数位数8B 模型权重相对 FP16典型场景
FP16 / BF161616 GB1×训练、精度敏感推理
FP888 GB2×H100 原生支持，几乎无损
INT888 GB2×通用推理
INT4（GPTQ/AWQ）44 GB4×单卡部署、端侧

量化的难点不是"把数字变小"，而是"变小之后精度不崩"。两种主流做法：

  • GPTQ：逐层做，用一小批校准数据，最小化量化误差对输出的影响（二阶信息）；
  • AWQ：观察到只有约 1% 的"显著权重"重要，按激活幅度找出它们并保护，其余大胆量化。

注意量化的收益和 batch 有关：权重占读取量的大头时（batch 小、上下文短），4bit 几乎能把解码速度提到 4 倍；但当 batch 很大、KV cache 读取占据主导时，只量化权重就不够了，得连 KV cache 一起量化——那是第 11 章的主题。

投机解码：小模型先试写

解码慢是因为"一次只生成一个 token，却要读一遍全部权重"。投机解码（speculative decoding）的思路是：让一个小模型（草稿模型）快速猜出接下来 4 个 token，然后让大模型一次前向并行验证这 4 个。验证的计算量和生成 1 个差不多（因为都是一次前向），但可能一次接受多个。

\[ \text{speedup} \approx \frac{1-\alpha^{k+1}}{(1-\alpha)(1+kc)} \] 10.3

其中 \(\alpha\) 是草稿被接受的概率，\(k\) 是每轮猜几个，\(c\) 是草稿模型相对大模型的开销比例。取 \(\alpha=0.8\)、\(k=4\)、\(c=0.05\)，加速比约 2.6 倍。关键性质：输出分布和原模型完全一致——它不是近似，是用拒绝采样保证等价。

草稿不一定是另一个模型。也可以用同一模型的低精度版本、n-gram 查表、甚至"提示词里已有的片段"来猜，这类方法统称 draft-free 投机解码。还有一类做法（Medusa、EAGLE）是在模型上挂几个额外的预测头，一次吐出多个位置的候选，再用树状注意力并行验证——本质相同，都是"用并行验证换串行生成"。

要注意它的收益是有条件的：batch 越大，投机解码的收益越小。因为大 batch 下 GPU 已经被"多个用户的解码"填满，空出来的算力变少，而投机解码吃的正是空闲算力。

连续批处理与调度

传统批处理要求一个 batch 里所有请求同时开始、同时结束。但生成任务的输出长度差别极大，短请求完成后 GPU 就在等长请求，利用率暴跌。

连续批处理（continuous batching）把调度粒度从"请求"降到"每一步"：某个请求生成完就立刻退出，队列里的新请求立刻补进空位。配合 PagedAttention，显存也能按块回收。这是 vLLM、TensorRT-LLM、SGLang 吞吐提升 10 倍以上的主要原因。

调度器在做的事，是在三个约束之间找平衡：显存能装下多少条序列、算力每步能算多少 token、用户能忍受多长的等待。

  • 显存：KV cache 决定了每张卡能挂多少个序列（第 11 章会给出可并发数的公式）；
  • 公平：新请求的 prefill 会打断正在解码的请求，造成 TPOT 抖动，所以有了 chunked prefill（把长输入切成小块，和解码混在一起跑）；
  • 回收：显存不够时不是杀掉请求，而是 preemption——把某个请求的 KV 换出到 CPU（swap）或直接丢掉重算（recompute）。长上下文请求重算很贵，所以工业系统通常优先换出短请求。

小结

prefill 是算力密集，decode 是带宽密集，解码几乎总贴在 roofline 的斜线上。后面的四种手段各自换掉一样东西：FlashAttention 换执行顺序，让 \(T\times T\) 的矩阵不落地；量化换精度，少读字节；投机解码换并行，用小模型猜、大模型验；连续批处理换调度，把总带宽切成很多条流。它们互不冲突，可以叠加，但权重用量化与投机解码的收益都会随 batch 变大而衰减。KV cache 是这一切背后的隐形成本，第 11 章单独拆开讲。
