第二十一章 · Harness 工程

Harness：模型外面那一圈代码

第 20 章讲的是 agent 的原理，这一章讲怎么把它做成能长期运行的东西。模型能力决定上限，外面这层代码决定你能否稳定地接近这个上限：同一个模型，harness 写得粗糙，任务成功率可能从 60% 掉到 20%，成本翻三倍，也可能在某次操作里误删你的文件。

harness 由哪些部分组成

harness 指的是模型之外、业务之内的全部代码。按"哪里会出问题"来分，大致是下面几块：

部件职责坏了会怎样
会话与事件流记录每一轮的消息、工具调用、结果与状态排障时无迹可查，无法回放
主循环调模型 → 解析动作 → 执行 → 回填 → 判停死循环、预算失控、提前收工
工具运行时参数校验、执行、截断、错误包装模型拿到无法修复的错误信息
执行环境沙箱、文件系统、shell、网络边界越权、误删、数据外泄
模型网关选模型、重试、限流、缓存、记账延迟抖动、成本不可控
观测与评测指标、轨迹、回归任务集改一处坏另一处，且无人知晓

主循环

删掉所有花哨的部分，主循环二十行就能写完：

def run(task, tools, budget):
    messages = [system_prompt(tools), user(task)]
    for step in range(budget.max_steps):
        if budget.exceeded(messages):        # 上下文或花费超限
            messages = compact(messages)      # 先压，再继续
        reply = model.chat(messages, tools=tools.schema())

        if not reply.tool_calls:              # 模型说完了
            return finish(reply.text)

        for call in reply.tool_calls:         # 可能并行多个
            if not permitted(call):           # 权限门
                messages.append(tool_error(call, "需要审批"))
                continue
            out = tools.run(call)             # 执行 + 截断 + 错误包装
            messages.append(tool_result(call.id, out))
    return abort("超过步数预算")

这二十行里有四处必须做对，每一处做错都能单独毁掉体验：

决定怎么做做错的后果
什么时候停模型不再调工具；或达到步数/花费/时间上限无限循环烧钱，或改一半就交差
什么时候压窗口用量到 70%–85%，或下一步输入预计超额工具结果被挤爆，报一个看不懂的错
错误怎么回结构化错误 + 修复线索 + 是否可重试模型重复同一个错误动作到死
并行怎么处理同一批 tool_call 并发执行，结果按 id 回填串行执行把延迟放大 3–5 倍

工具怎么设计

  1. 少而正交。十个边界清晰的工具，胜过四十个互相重叠的。工具一多，模型选错的概率就上去了，schema 本身也吃上下文。
  2. 幂等。"读文件"随便调一百次都安全；"发邮件"必须要求显式确认。副作用的工具要能被识别出来。
  3. 返回值有上限。任何工具都必须有截断策略（行数、字节数、结果条数），并在截断处明确标注"还有多少没显示"。
  4. 错误要可修复。"invalid input" 是无用信息；"path 必须是相对路径，你传了绝对路径 /etc/passwd" 才能让模型下一轮改对。
  5. 结构化。稳定的字段（status / stdout / stderr / exit_code）比一段自由文本好解析，也好压缩。
  6. 可组合。让"搜索—读取—编辑—验证"能自然串成一条链，模型就会自己发明出工作流。
  7. 危险动作显式化。删除、覆盖、提交、推送、花钱——这些必须是独立工具，而不是藏在某个参数里的隐式行为。

权限与沙箱

agent 会执行模型写出来的命令，等于把 shell 交给一个概率模型。稳妥的做法是按危害分级，而不是去判断哪条命令"恶意"。

档位允许什么典型场景兜底
只读读文件、搜索、跑无副作用的查询代码问答、代码审查文件系统只读挂载
工作区可写在工作目录内改文件、跑构建与测试日常编码任务目录级沙箱 + 网络受限
完全访问任意路径、任意命令、联网部署、环境修复人工审批 + 审计日志 + 可回滚

还有三条细节值得单独说：

  • 审批要做得足够具体。弹窗里要写清将要执行的确切命令和影响范围，能记住"这类操作本次会话内都同意"，也要能一键拒绝并让模型换条路走。
  • 外部内容一律当数据。网页、issue、依赖包里的 README 都可能写着"忽略之前的指令"。harness 必须把这些内容标记为不可信输入，且不让它触发工具调用链——这就是 prompt injection 的第一道防线。
  • 凭据不进上下文。环境变量、token 由 harness 在执行时注入，永远不要拼进 prompt。否则一次日志回吐就是一次泄露。

上下文管理：压缩什么

第 20 章说上下文是瓶颈。harness 里应对它的手段是压缩（compaction）：到了阈值，用模型把早先的对话摘要成一段，替换掉原始消息。做得好与差，差别全在保留什么。

必须保留

  • 用户的原始目标与硬约束（"不要改公共 API"）
  • 已经做出的决定与理由
  • 当前进行到哪一步、还剩什么（TODO）
  • 关键文件路径与行号
  • 失败过的尝试（避免重蹈覆辙）

可以丢

  • 已经执行过的工具的原始输出
  • 重复读过的文件内容
  • 中间过程的推理草稿
  • 报错日志的全文（留错误类型与首行）
  • 寒暄、确认、无关的搜索结果
压缩要解决的问题

压缩的目的不是少花 token，而是把已经消耗掉的输出从之后每一步的上下文里删掉。所以宁可让模型多跑几步、多调一次工具，也不要把大块输出留在上下文里。

子系统按需加载

真实 harness 往往带几十个扩展：特定领域的技能、插件、MCP 连接的外部工具。全部写进系统提示，光 schema 就吃掉几万 token——而且 90% 的任务根本用不到。

通行的做法是先给索引：系统提示里只写"有哪些能力、什么条件下用"的一行说明，通常几十个 token；真正用到时，再由 harness 把完整说明注入上下文。插件、hook、MCP 工具的完整 schema 也一样，第一次调用时才加载。

机制典型作用加载时机
Skill / 技能包某个领域的操作手册与脚本任务命中领域时按需注入
MCP / 外部工具把第三方能力接成工具首次需要时握手、拉 schema
Hook / 生命周期钩子在工具调用前后做校验、记账、通知常驻，但要轻
子代理把探索性工作隔离到独立上下文里跑任务可拆分时派发

子代理与并行

子代理最大的价值是上下文隔离，而不是并行加速：一个子代理读了四十个文件、试了五种方案，最后只把一段结论交回父代理。父上下文里多了一条消息，而不是几万 token 的探索过程。

一次"搜索 + 试错"的隔离效果
子代理内部消耗
约 12 步、平均 15K 输入 ≈ 18 万 token 的读入
回传父代理
一段 400 token 的结论 + 两个文件路径
对父上下文的增长
≈ 0.4K，而不是 12 步 × 15K
代价
子代理看不到父代理的全部上下文，需要把必要前提写进任务描述

并行的边界也要划清：读操作可以随便并行；写操作并行就会冲突（两个子代理改同一个文件）。常见折中是"并行探索、串行修改"，或者按文件/目录切分所有权。

事件流与回放

agent 出问题时，最有用的不是"再跑一遍看看"，而是一份完整的轨迹：第几步、输入多长、调了什么工具、参数是什么、返回了什么、花了多久、多少钱。这就是事件流（session events）的价值。

  • 可回放：把轨迹重放，能在不打模型的情况下复现解析、权限、截断逻辑的 bug。
  • 可审计：谁在什么时候让 agent 改了什么，必须能查。这在团队环境里是硬需求。
  • 可归因：失败到底是模型选错工具、工具返回噪声、还是 harness 解析错？没有轨迹就只能猜。

一个实用的判据：如果一个 bug 你没法只靠轨迹看出来，说明观测还不够。

harness 与推理层的接口

harness 的设计直接决定推理层的前缀缓存能不能命中——这是两个团队最容易互相甩锅的地方。

harness 的做法对推理层的影响
系统提示与工具 schema 固定、顺序稳定前缀缓存稳定命中，输入成本降到约 1/10
每步动态改写系统提示（插入时间、随机 id）前缀失效，每一轮都按全价重算
把大段工具结果整块塞进历史每步输入变长，TTFT 与成本一起涨
一次并行发多个 tool_call工具往返串行变并行，端到端延迟明显下降
压缩时重写整段历史缓存全部失效一次，之后重新累积（可接受，但别频繁做）

怎么评测 harness

harness 的回归测试不能只测函数返回值，还要测整条轨迹的行为。够用的配置有三部分：

  1. golden tasks：20–50 个真实任务，每个都有可自动判定的终态（跑测试、比对 diff、检查文件存在）。
  2. 轨迹断言：除了终态，还要断言"必须跑过测试""不许修改断言文件""工具调用次数不超过 N"。
  3. 成本与延迟门槛：每个任务记录 token 与耗时，超过基线 30% 就报警——性能退化往往先于质量退化出现。

跑评测时最容易被忽略的一点：模型换了、提示词改了、工具描述改了，都算线上变更，都要过这套回归。很多"模型变笨了"的抱怨，最后追到的是某个工具的描述被顺手改短了。

踩过的坑

经验为什么
先做停止条件，再做能力没有停止条件的 agent 是烧钱机器
工具宁少勿多，描述宁长勿短工具数量影响选择准确率，描述质量影响参数正确率
所有工具输出都要截断一条没截断的日志能毁掉整次任务
错误信息写给模型看，不是给人看模型是下一个读者，它需要的是"怎么改"
状态写文件，别写记忆里上下文会丢，文件不会
危险操作单独建工具才能拦、才能审、才能回滚
外部内容默认不可信prompt injection 的第一道防线
每次变更都跑 golden tasks提示词与工具的改动比模型升级更常见
先修观测，再修 bug没有轨迹的修复都是猜
成本是一个功能指标成功率相同、成本五倍，就是两个产品
小结

harness 就是模型之外那圈代码：会话、主循环、工具运行时、执行环境、模型网关、观测评测，每一块都有各自的坏法。主循环里只有四处需要判断——什么时候停、什么时候压缩、错误怎么回、并行怎么处理。安全靠分级而不是靠识别：只读、工作区可写、完全访问，危险动作单独做成工具，外部内容一律当数据。压缩的意义在于把已消耗的输出从之后每一步的账单里删掉；前缀是否稳定决定成本能省下多少；没有轨迹和 golden tasks，调 harness 就只是在凭感觉猜。
