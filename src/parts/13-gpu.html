第十三章 · GPU 执行

GPU 执行：一次 decode 是怎么落到硬件上的

前面几章在算"要多少显存、要多少带宽"。这一章往下走一层：一次 decode step 从 Python 里的几行代码，到 GPU 上几百个 kernel 执行完，中间经过哪些层、每一步花多少时间、哪里会空转。理解了这一层，才能解释 CUDA graph、pinned memory、NCCL 和 kernel 融合为什么会出现在每一个推理引擎里。

调用链：五层，每层只做一件事

推理引擎自己不直接和显卡打交道。它写的每一行 y = x @ w，都要穿过五层才变成 SM 上的指令。把这条链拆开，出问题时才知道该看哪一层：

层具体是什么这一层做什么出问题的症状
推理引擎vLLM 的 EngineCore、SGLang 的调度器决定这一步算哪些 token、准备输入张量调度慢，GPU 出现空档
框架PyTorch 的 aten 算子与自动微分无关部分把 matmul 拆成一次 GEMM 调用Python 开销大，每秒只跑几十步
CUDA 运行时libcudartcudaLaunchKernel、cudaMemcpyAsync、流与事件同步点选错，每步多几毫秒
CUDA 驱动libcuda + 内核模块 nvidia.ko把命令写进 GPU 的命令队列，管理 context 与显存版本不匹配、PCIe 降速、显存碎片
GPU 硬件GigaThread 引擎、SM、HBM把 block 分到 SM，由 warp 执行见第 10 章的带宽与算力瓶颈

关键的一点：CPU 从来不等 GPU 执行完。它只是把一条条命令写进显卡的命令队列，写完就返回。一次 kernel launch 在 CPU 侧只花 3–8 微秒，而 GPU 执行它可能要几十微秒。正常情况下 CPU 跑在前面，队列里一直堆着活；一旦 CPU 提交得比 GPU 执行得慢，GPU 就会空转——这类问题被称为"提交受限"，下一节会算它。

把第 8 章的逐层前向换成"kernel 视角"：每一层被拆成若干个核函数，每个核函数有自己的 grid、block 和内存访问模式。以单请求 decode（batch = 1）为例：

这些 kernel 是谁写的

推理引擎不会自己实现矩阵乘，它站在一批库的肩上。认识这几个名字，看日志和性能剖析时就不会迷路：

为什么 decode 的 GEMM 这么特殊？因为它的 M 维只有 1（一条序列一个 token）。一个 \([1,4096]\times[4096,4096]\) 的矩阵乘，要读 32 MB 权重，只做 1600 万次乘加——算术强度约 1 FLOP/字节，而 H100 的脊点是 295。这意味着它完全被带宽限制，Tensor Core 的算力大部分时间在等数据。推理引擎的大部分优化（量化、GQA、投机解码、更大 batch）本质上都是在提高这个比值。

显存从哪里来，拷贝怎么走

启动时，PyTorch 的缓存分配器会先用 cudaMalloc 向驱动申请大块显存，之后所有张量都从这块池子里切，释放时归还池子而不是还给驱动——这就是为什么 nvidia-smi 显示的占用几乎不下降，也是"显存碎片"的根源。

vLLM 的启动流程能说明这个池子怎么分：先加载权重，再用一次 dummy run 测出激活峰值，剩下的显存按比例切给 KV 池。这也是为什么改 max-model-len 会连带影响并发数——池子大小没变，每序列占的块变多了。

主机到设备（H2D）的拷贝有两条路径。普通内存（pageable）不能直接被 DMA 读取，驱动要先复制到一块固定的中转缓冲区，等于多走一趟；锁页内存（pinned，用 cudaHostAlloc 分配）才可以被直接 DMA，拷贝是真正异步的。时间可以按带宽估算：

\[ t_{\text{H2D}} \approx \frac{S}{BW \times \eta}, \qquad \eta \approx 0.8 \] 13.1
链路单向带宽1 MB 的拷贝时间典型场景
PCIe 4.0 ×1625 GB/s≈ 50 微秒单机消费级卡、A100 PCIe
PCIe 5.0 ×1650 GB/s≈ 25 微秒H100 PCIe、新一代服务器
NVLink 4（H100）450 GB/s≈ 3 微秒GPU 之间、部分 CPU-GPU 互联
NVLink-C2C（Grace Hopper）450 GB/s≈ 3 微秒CPU 与 GPU 共享内存空间

一步 decode 要传的东西并不多：token id、位置、KV 槽位映射、分页表、序列长度，加上采样回来的一个 token。以 batch 64、每条序列最多 1024 个块为例，分页表是 \(64 \times 1024 \times 4\) 字节 = 256 KB，其余都是几百字节，PCIe 4.0 下总共约 10 微秒。真正贵的是同步：如果每步都把 logits 拷回 CPU 再采样，128256 维 fp32 是 500 KB，而且这次拷贝默认是同步的，会把流水线打断。

流、事件与两种空转

CUDA 的流（stream）就是命令队列：同一个流里的命令按顺序执行，不同流之间可以并发。PyTorch 每个线程有一个"当前流"，推理引擎就在这个流上提交算子；NCCL 有自己的流，跨流要用事件（event）对齐。

同步有三个层次：cudaStreamSynchronize 等整个流，cudaEventSynchronize 只等某个点，还有一些隐式同步——cudaMalloc、pageable 内存的拷贝、默认的 cudaMemcpy 都会把队列排空。推理引擎的性能问题，很多都是这类"看不见的同步"造成的。

把一步的时间写成模型，就看得很清楚：

\[ T_{\text{step}} \approx \max\left(N \cdot t_{\text{launch}},\; N \cdot t_{\text{kernel}}\right) + t_{\text{sync}} \] 13.2

其中 \(N\) 是这一步的 kernel 数，\(t_{\text{launch}}\) 是 CPU 提交一个 kernel 的时间（3–8 微秒），\(t_{\text{kernel}}\) 是 GPU 执行一个 kernel 的时间。当 \(N \cdot t_{\text{launch}}\) 超过 \(N \cdot t_{\text{kernel}}\) 时，GPU 就有空档——这就是"提交受限"。用下面的滑条算一下：8B 单请求 350 个 kernel，GPU 每个 15 微秒（合计 5.25 毫秒），如果 CPU 每个要 15 微秒提交，两者打平；Python 层再慢一点就开始拖后腿。

CUDA graph：把几百次启动压成一次

CUDA graph 的思路很直接：把一段 kernel 调用序列"录"下来，变成一个带依赖关系的有向无环图，之后用一次 cudaGraphLaunch 回放。录制时用流捕获（cudaStreamBeginCapture），把真实计算跑一遍；回放时 GPU 按图里的依赖自己调度，不再需要 CPU 逐个提交。

代价是三个约束：地址固定（所有输入输出张量必须在捕获时就位，回放时只改内容不改指针）、形状固定（所以按 batch 大小分档捕获，实际 batch 不够就 padding 到某一档）、不能有动态控制流（Python 的 if 和循环必须提前决定）。

注意力是进图最难的一步：分页 KV 的块表每步都在变。但只要块表放在固定的显存地址上（内容变、指针不变），kernel 从固定地址读表，图就能回放——这也是 FlashAttention 的 varlen 接口和 FlashInfer 的 plan/run 两段式设计存在的原因。

vLLM V1 把这件事做成了五种模式，按批次形态自动选择：

模式捕获什么适合
NONE不捕获，逐条 eager 执行调试、不支持图的后端
PIECEWISE除注意力以外的所有段注意力后端不支持图时的通用选择
FULL整模型一张图（prefill 与 decode 分批）小模型、短 prompt、低延迟场景
FULL_DECODE_ONLY只给纯 decode 批次建图P/D 分离里的 decode 实例
FULL_AND_PIECEWISEdecode 用整图，其余用分段图默认；性能最好，显存与启动代价也最高

V1 的默认是 FULL_AND_PIECEWISE（分段编译可用时）；分段编译不可用时退回 NONE。具体能不能建整图，取决于注意力后端的能力等级：FlashAttention 3 对任意批次都支持，FlashAttention 2 只支持同构批次，FlashInfer 只支持单 token decode，Triton 注意力两端都支持。引擎会自动把模式"降级"到后端支持的那个——这就是同一个版本在不同后端上行为不一样的原因。

捕获的粒度也分两种：纯 decode 批次按请求数分档（1、2、4、8……到 max-num-seqs），prefill 或混合批次按 token 数分档。运行时拿批次描述符（token 数、请求数、是否同构）去查最小的一张能覆盖它的图；查不到就退回 eager。

代价也能量化

每张图都要一份静态输入缓冲，捕获时还要显存峰值与一次 dummy run。所以 FULL_AND_PIECEWISE 启动最慢、占显存最多，但低延迟场景收益最大；反过来，batch 很大、GPU 本来就忙时，图的收益会被摊薄。

引擎侧：CPU 每步在干什么

vLLM V1 的进程结构值得记一下，因为它决定了 CPU 核数怎么配：HTTP 接口在一个 API 进程里，调度与 KV 管理在 EngineCore 进程里，每张卡一个 worker 进程。总进程数是"API + DP + 卡数（+1 个协调进程）"。4 卡单机是 1 + 1 + 4 = 6 个进程。

进程数量做什么
API 服务默认等于 DP收发 HTTP、分词、流式返回，用 ZMQ 与 EngineCore 通信
EngineCore等于 DP调度器、KV 池管理、组织这一步的输入
GPU worker等于卡数加载权重、准备张量、执行前向、管理显存
DP 协调DP > 1 时 1 个数据并行的负载均衡

调度器是"按 token 预算"工作的：每步在 max-num-batched-tokens 的预算里挑请求，不区分 prefill 和 decode 阶段，缺多少 token 就补多少。这一步同时实现了 chunked prefill、前缀缓存和投机解码。

然后是异步调度：GPU 执行第 \(N\) 步的同时，CPU 已经在排第 \(N+1\) 步的计划，并用"占位 token"先把位置占住，等第 \(N\) 步的结果出来再填回去。这样 CPU 的调度时间就被藏在 GPU 的时间里。采样也放在 GPU 上做：只把采样出来的 token id 取回，而不是把 12 万维的 logits 搬回 CPU——后者的代价前面算过，500 KB 加上一次同步。

多卡：一次 all-reduce 要多久

张量并行把每层的权重切成两半：QKV 与 FFN 升维按列切，输出投影与 FFN 降维按行切。这个切法决定了每层要做两次 all-reduce，把两半的中间结果加起来。

通信量可以精确算。对一个 hidden 维 \(d\)、batch×序列 \(B\cdot S\) 的张量，一次 all-reduce 每个 rank 收发的字节数约为：

\[ V_{\text{token}} \approx 2 \times 2 \times 2 \cdot L \cdot d \;\text{(字节, fp16, batch=1)} \] 13.3

代入 Llama 3 8B（\(L=32\)，\(d=4096\)）：每个 token 约 1 MB。听上去不大，但延迟才是问题：单次 all-reduce 在 NVLink 上约 10 微秒，一层两次、32 层就是 64 次，合计 0.6 毫秒——相对 4.8 毫秒的 GPU 时间已经占了一成多；换成 PCIe，单次 30–60 微秒，光通信就要 2–4 毫秒，几乎和计算持平。

互联单次 all-reduce 延迟32 层 × 2 次结论
NVLink 4≈ 10 微秒≈ 0.6 毫秒单机多卡可用，但已不可忽略
PCIe 4.0≈ 30–60 微秒≈ 2–4 毫秒把计算时间吃掉大半
跨机 InfiniBand≈ 50–100 微秒≈ 3–6 毫秒只适合大 batch 摊薄

所以 batch 越大，TP 越划算：通信量随 batch 线性增长，但延迟基本不变，每个 token 分摊到的通信开销随 batch 下降。反过来，单用户低延迟场景下 TP 越大越慢。工程上的对策有三个：用共享内存实现的自定义 all-reduce 省掉一次往返、Hopper 的 NVLS 多播让一份数据同时到达所有卡、以及干脆把 prefill 和 decode 拆到不同实例上（P/D 分离）。

硬件特性：同样的 FLOPs 为什么快慢差很多

H100 的 fp16 稠密算力是 989 TFLOPS，fp8 是 1979 TFLOPS，HBM 带宽 3.35 TB/s；A100 分别是 312 TFLOPS 和 1.5 TB/s。这些数字背后是几个具体机制：

机制做什么对推理的影响
Tensor Core每个 SM 4 个，一个周期完成一块矩阵乘加大 batch 的 prefill 靠它；单请求 decode 用不满
FP8 与 block scale8 位浮点，配 per-tensor 或 per-block 缩放权重与 KV 减半，带宽瓶颈直接减半
TMA（Hopper）异步整块搬运，不占寄存器和指令槽GEMM 与注意力的流水线更满
warp 专用化一部分 warp 负责搬运，一部分负责计算FlashAttention 3、CUTLASS 的常规做法
占用率与波次SM 上同时驻留的 block 数、grid 分几波跑grid 太小、尾波不满都会浪费算力

最后一条在 decode 里特别明显。一个 \([1,4096]\times[4096,4096]\) 的 GEMV，如果按 128 个线程一个 block，只有 32 个 block，而 H100 有 132 个 SM——第一波就把 SM 用掉不到四分之一。波次效率可以写成：

\[ \text{效率} = \frac{g}{SM \times b \times \left\lceil g / (SM \times b) \right\rceil} \] 13.4

其中 \(g\) 是 block 数，\(b\) 是每个 SM 能同时驻留的 block 数。把 \(g=32\)、\(SM=132\)、\(b=1\) 代进去，效率只有 24%。解决办法是拆 K 维（split-K）把 block 数做大，或者干脆把 batch 做大——这也解释了为什么同样的模型，服务端的吞吐远高于单请求。

观测：先看间隙，再看单核效率

性能问题分两类：GPU 没吃饱（等 CPU、等通信、等采样），和 GPU 吃饱了但效率低（带宽浪费、占用率低）。前者看时间线，后者看单 kernel 指标。

工具看什么典型问题
Nsight Systemskernel 时间线与间隙、流并发、拷贝、NCCLkernel 之间有毫秒级空洞 → 提交受限或同步点
Nsight Compute单 kernel 的 DRAM 吞吐、占用率、Tensor Core 利用率带宽打满但算力闲置 → 该量化或改 batch
DCGM / nvidia-smi dmonSM 利用率、显存带宽、功耗、温度利用率长期 30% 以下 → 先怀疑 CPU 与调度
torch.profiler / CUPTIPython 侧每个算子的耗时与调用次数算子太碎、Python 开销大 → 融合或上 graph
CUDA_LAUNCH_BLOCKING=1把异步变同步，定位是哪个 kernel 出错调试用，会让整个程序慢一个量级

一个实用的顺序：先用 Nsight Systems 看一步里 kernel 的排布，如果间隙大于单个 kernel 的时间，问题在 CPU 或同步；如果间隙很小但 SM 利用率低，再看 Nsight Compute 里 DRAM 吞吐是否打满——打满就是带宽问题，没打满才是并行度或延迟问题。

注意力在引擎里：三类 kernel，两套形状

前面把一次 decode 拆成了几百个 kernel，但没有展开其中最特殊的一个——注意力。它和 GEMM 不一样：矩阵乘的输入形状是固定的，而注意力的输入里有一个“长度可变的维”（上下文），每来一个请求这个维就变一次。推理引擎对注意力的实现，本质上就是怎么在形状不断变化的 KV 上，喂给一个高效的 kernel。

先分清三种负载，它们的 kernel 完全不同：

阶段q 的形状主要计算瓶颈典型 kernel
prefill（整段提示词）[T, d]QKT 是 [T,T] 的大矩阵乘，再乘 V算力FlashAttention 的 prefill 路径、causal GEMM
decode（一次一个 token）[1, d]q 和 T 个 k 逐个点积 → 加权求和带宽（读整段 KV）分页 decode kernel、FlashDecoding、XQA
chunked prefill（切块预填）[c, d]块内是 [c,c]，块间只读历史 KV两者混合同一个 kernel 带“query 长度 > 1”的路径

这三行解释了一个常见困惑：为什么同一个模型，prefill 能吃满 GPU、decode 却只有个位数利用率。prefill 的 \(QK^{\top}\) 是一个 [T,T] 的方阵乘，\(T\) 上千时张量核心吃饱；decode 的 q 只有一行，\(q\cdot k_j\) 是一串点积，算的时候要先把 128 KB 的 KV 从显存搬进 SM——算得少、搬得多。

分页：block table 与两套内存布局

引擎不预分配“最大长度的连续 KV”，而是把 KV 切成固定大小的块（vLLM 16 个 token 一块），按需分配、散落存放。于是每个请求手里有一张 block table：逻辑块号 → 物理块号。这一步把“逻辑上连续的前缀”和“物理上离散的显存”解耦了，才让前缀缓存、抢占、共享前缀成为可能（第 11 章）。

写入和读取用的是两套索引：

  • 写：新 token 的 KV 由 slot_mapping[token] 指定“写到哪个物理块的哪个槽位”，写完之后 block table 里就多了一项。
  • 读：kernel 拿到 block table，按逻辑块号查物理块号，再去显存里取那 16 个 token 的 k/v。

两种布局还不同。以早期 vLLM 的 kernel 为例：k_cache 的布局是 [物理块, KV 头, d/x, 块内位置, x]，v_cache 是 [物理块, KV 头, d, 块内位置]；前者为了“同一线程组连续读 16 字节”做了向量化重排，后者是列主序（因为 V 要和权重按列做内积）。这不是实现细节，而是布局决定了访存能不能合并——同样的 128 KB，合并读和非合并读差好几倍。

GQA 在这里显形：kernel 启动时按查询头数开网格，但取 K/V 时用 kv_head = q_head / group_size 把 8 个查询头映射到同一份 KV。所以 GQA 省的不只是显存，还有 decode 时实际读进来的字节数——8 个头共享一份，读取量就是原来的 1/4。

decode kernel 的内部：一个 warp 管一块，两级归约

以分页 decode kernel 为例，一个线程块负责“一个请求 × 一个头”的整段上下文，网格是 (头数, 请求数, 分区数)。块内再分工：

  • 一个 warp 负责一个物理块（16 个 token），多个 warp 轮流覆盖整段上下文；
  • 一个 线程组（2 个线程）合作算一个 \(q\cdot k_j\)：各自算一半维度，再用 shuffle 归约成完整的点积；
  • softmax 分两级：先在 warp 内用 shuffle 求 max 和 sum，再通过共享内存跨 warp 归约——这就是 FlashAttention 的“在线 softmax”在分页场景下的写法；
  • V 的加权求和按列做：每个线程负责若干行（head 维度），把同一批 token 的 logits 和 value 做内积累加。

上下文很长时，一个线程块跑完整段会占满一个 SM 太久，于是再切分区（split-K）：把 T 切成几段并行算，每段得到“部分 max、部分 sum、部分输出”，最后用一个小的合并 kernel 按 \(e^{m_i-M}\) 重新加权求和。FlashDecoding 与 vLLM 的 max_num_partitions 就是这件事。它的代价是多一次 kernel 启动和一次额外的显存读写，收益是把长上下文的 decode 从“一个 SM 慢慢扫”变成“多个 SM 并行扫”。

后端怎么选：能力枚举比名字重要

vLLM 把注意力实现做成可插拔的 backend，按优先级自动选，也可以手动指定（--attention-backend FLASH_ATTN 或 -ac.backend=FLASHMLA，两者互斥）。选型的判据不是“哪个快”，而是你的配置是否被它支持：dtype、KV dtype、head size、块大小、是否要 sink、是否非因果、是否多模态前缀、是否稀疏。指定了不兼容的后端会直接报错并给出原因，例如“compute capability not supported”。

后端典型场景要注意的
FlashAttention 2 / 3 / 4标准 MHA/MQA/GQA；默认首选版本按硬件选：SM100+ 用 FA4、SM90 用 FA3、其余 FA2
FlashInferdecode 路径（XQA）、需要 sink 或特定块大小SM100 上可用 trtllm-gen；XQA 可单独关掉
Triton没有专用 kernel 的形状、调试、自定义可移植性好，峰值性能通常略低
FlashMLA / Triton MLADeepSeek 系 MLAprefill 与 decode 用不同后端，分开选
复合后端多模态前缀（图像要双向注意力）同一个 batch 按“当前 query 是否需要双向”路由到不同子后端

还有一个容易被忽略的耦合：后端决定了 CUDA graph 能不能捕获。不同后端对“批次形状是否统一”的要求不同，能力大致分四档——始终可捕获（ALWAYS）、只要批次统一就可捕获（UNIFORM_BATCH）、只有单 token decode 可捕获（UNIFORM_SINGLE_TOKEN_DECODE）、不可捕获（NEVER）。FlashAttention 3 属于第一档，FlashAttention 2 属于第二档，FlashInfer 的单 token 路径属于第三档，Triton 属于第一档。选了一个不可捕获的后端，等于放弃了 CUDA graph 那部分收益（第 13 章前面算过：提交受限时能差 20%）。

MLA 还有一处和标准注意力不同的实现形态：decode 时走“吸收”形式——不把潜向量还原成 128 个头的 K/V，而是把投影矩阵预先吸收进 q 与输出侧，每步只读 576 个数（第 11 章）。所以 MLA 的 prefill 与 decode 常常用两个不同的 kernel：prefill 用解出 K/V 的常规形式（矩阵大、张量核心利用率高），decode 用吸收形式（读取少）。引擎里这也是两套后端配置。

这一章的要点

一次 decode 在 GPU 上是几百个 kernel，每个只有十几微秒，所以"怎么把 kernel 提交上去"和"kernel 本身快不快"同样重要。CPU 侧的开销用 CUDA graph 压掉，GPU 侧的浪费靠融合、量化和更大的 batch。多卡时还要加上每层两次 all-reduce 的延迟，它和 batch 大小成反比，决定了 TP 该开多大。
