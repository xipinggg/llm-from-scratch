*第二十章 · Agent 工程*

# Agent：让模型动手做事

前十六章都在回答"模型怎么算出一个 token"。这一章换一个问题：怎么让一个只会输出文本的模型，在真实环境里连续做完一件需要二十步的事。靠的不是更大的模型，而是"模型 + 工具 + 循环 + 环境"这套系统，也就是 agent。

## agent 是什么

去掉各种包装，一个 agent 需要的东西并不多：模型决定下一步做什么，工具把决定变成真实动作，循环把结果送回模型，环境提供文件和命令，预算限制花销，停止条件负责收尾。缺了任何一样，它都会变成别的东西——只会聊天，或者只会盲目执行。

> **单次调用**
> 一次任务 = 一次前向。错了只能再问一次，模型看不到自己刚才造成了什么后果。能力上限是"一次说对"。
> 成本可预测、延迟稳定、评测容易。

> **Agent**
> 一次任务 = N 次前向 + N−1 次环境交互。每一步都能看到上一步的真实结果，于是"改错"变成了循环的一部分。
> 成本随步数增长、方差大、必须评测轨迹。

| 维度 | 单次调用 | Agent |
| --- | --- | --- |
| 能力来源 | 一次前向的深度 | 步数 × 每步一次前向 |
| 错误处理 | 只能重问 | 观测 → 纠正 → 继续 |
| 能做的事 | 仅"说" | 读写文件、跑命令、调 API |
| 成本 | 基本恒定 | 与步数、上下文长度成正比 |
| 主要风险 | 答错 | 答错、跑偏、破坏环境、烧钱 |
| 评测方式 | 答案对错 | 终态 + 轨迹 + 成本 |

## 为什么多走几步反而更可靠

第 18 章讲过思维链：把中间推理写出来，用生成的 token 换计算深度。agent 用的是同一个思路，但多了一样思维链没有的东西：来自环境的真实反馈。思维链里写下"1+1=3"没有人会纠正它；agent 写完代码跑一下测试，编译器会立刻告诉它错了。

多步之所以有用，靠的是三件事：

- **把状态写出去。**把"已经改了哪三个文件、还剩哪两件事"写进文件或待办清单，而不是指望上下文记住。上下文会被压缩、会被截断，文件不会。
- **中间结果可以验证。**测试通过、命令退出码为 0、diff 只动了预期的地方——这些都是客观信号，能把“看起来对”变成“确实对”。
- **纠错闭环。**错误不再是终点，而是下一轮的输入。这直接把"一次成功率"换成了"多次收敛概率"。

> **工具的质量决定上限**
>
> agent 能做到什么程度，一半看模型，一半看工具返回的信息。工具吐出一万行日志，模型得在噪声里找那一行报错；工具直接返回"构建失败：第 42 行未定义变量 x"，模型下一步就能改对。同一个模型，工具设计差一个量级，任务成功率可以差一倍。

## 工具调用是怎么发生的

模型只会输出 token。所谓调用工具，其实是三方按同一个格式合作：

| 环节 | 谁负责 | 典型失败 |
| --- | --- | --- |
| **声明** | harness 把工具的 JSON Schema 放进系统提示 | 参数描述含糊 → 模型传错类型 |
| **生成** | 模型输出结构化的 tool call（名字 + 参数） | 格式漂移、漏字段、幻觉工具名 |
| **解析** | 推理框架的 tool parser 把文本块解析成对象 | 格式与 parser 不匹配 → 调用被当成普通文本 |
| **执行** | harness 校验参数、检查权限、实际调用 | 越权、路径穿越、超时、结果过大 |
| **回填** | 把结果作为 tool_result 追加进上下文 | 结果太长挤爆窗口；错误信息无法修复 |

工具声明就是一份普通的 JSON Schema。描述写得越具体，模型传参就越准：

```json
{
  "name": "read_file",
  "description": "读取一个 UTF-8 文本文件。返回带行号的内容；超过 2000 行只返回前 2000 行。",
  "parameters": {
    "type": "object",
    "properties": {
      "path": { "type": "string", "description": "相对仓库根目录的路径，例如 src/app.js" },
      "offset": { "type": "integer", "description": "1-based 起始行，默认 1" },
      "limit": { "type": "integer", "description": "最多返回行数，默认 2000" }
    },
    "required": ["path"]
  }
}
```

模型这一侧的输出则长这样（不同厂商的字段名略有差异，语义相同）：

```json
{"type": "tool_use", "id": "call_7f3a", "name": "read_file",
 "input": {"path": "src/app.js", "offset": 120, "limit": 60}}
```

> **部署时最容易踩的坑**
>
> 模型吐的是文本，能不能被正确解析成 tool call，取决于**推理框架的 parser 是否与模型的训练格式匹配**。vLLM 与 SGLang 都要显式指定 `--tool-call-parser`（第 12 章提过这类服务参数）。配错的典型现象是：模型明明"想"调工具，却输出一段被当作正文的 JSON，agent 循环原地打转。

## 每一步的钱和延迟花在哪

agent 每一步都要把全部历史重新喂给模型。这听起来很贵，好在历史的前缀通常不变，推理引擎的 KV cache 与 prompt caching 会按缓存价计算这部分输入（第 11、12 章）。成本大致可以写成：

$$
\text{cost} \approx \sum_{i=1}^{N}\Big(c_{\text{in}}\cdot |H_i| \cdot (1-\rho(1-d)) + c_{\text{out}}\cdot |O_i|\Big)
    20.1
$$

其中 $|H_i|$ 是第 $i$ 步的输入长度，$\rho$ 是缓存命中率，$d$ 是命中部分相对全价的比例。这个式子说明两件事：输入长度线性地推高成本；命中率决定这笔成本能省掉多少。

**一次 30 步任务的三个账本（假设：平均输入 20K token、每步输出 500 token）**

| 项 | 值 |
| --- | --- |
| 输入总量 | 30 × 20000 = **60 万 token**，这是 agent 最容易被低估的一项 |
| 输出总量 | 30 × 500 = **1.5 万 token**，只有输入的 2.5% |
| 模型耗时 | 30 × (0.4 s 首 token + 5 s 输出) ≈ **2.7 分钟** |
| 工具耗时 | 30 × 1.5 s ≈ **45 秒**，通常比模型耗时小一个量级 |
| 结论 | agent 慢在**输出的 token 数**与步数，而不是工具 |

这也解释了为什么缩短输出对 agent 收益很大：每步少输出 200 token，三十步就省下 6000 token 的生成时间，上下文也少长同样多。

## 上下文是最紧的那道限制

第 18 章说过，推理模型的成本主要压在思考 token 上；agent 的成本则主要压在历史长度上。一次任务的上下文大致由这几块组成：

| 组成 | 典型量级 | 怎么长起来的 |
| --- | --- | --- |
| 系统提示 + 工具 schema | 3–6 K | 固定，但每个工具都要几十行描述 |
| 历史推理文本 | 3–10 K | 每步的思考与解释，随步数线性增长 |
| 工具输出 | 10–60 K | 文件内容、命令日志、搜索结果——**增长最快** |
| 当前任务与约束 | < 1 K | 几乎不增长，却最不能丢 |

下面的图把这四块按任意一组参数画出来。拖动滑块，可以看到第几轮超过阈值：决定这一步的是阈值，不是窗口大小。

> **交互演示：上下文用量**（拖滑块看第几步撞墙） —— 在 HTML 版里可直接拖动 / 点击。

> **窗口大小不等于可用空间**
>
> 很少有人等到窗口全满才动手。工程上按窗口的 70%–85% 定压缩点：到了这个位置就压缩历史，否则下一步的工具输出就放不下。所以在同样的窗口大小下，压缩策略是否合适，往往比窗口本身更影响成败，这也是第 21 章 harness 要做的事。

## 工具输出先减噪再进上下文

工具返回的每个 token，在之后的每一步都会被重新支付一次。一份 30K 的文件读进上下文，后面二十步每一步都在为它付输入费、挤占窗口。所以工具层要先做减噪：

| 手段 | 做法 | 代价 |
| --- | --- | --- |
| 截断 | 只留头部与尾部若干行，中间标 "…省略 N 行…" | 可能漏掉中间的关键行 |
| 结构化 | 把日志压成"错误类型 + 文件:行 + 消息"三列 | 需要为每类工具写专用压缩 |
| 先检索后读 | 用 grep/glob 定位，再按行区间读文件 | 多一次工具往返 |
| 落盘再引用 | 大结果写进文件，上下文里只放路径与摘要 | 模型需要再读一次才能用 |
| 去重 | 同一文件第二次读只回变更部分 | 实现复杂，收益很大 |

## 记忆放在哪里

| 层 | 放什么 | 容量 | 失效方式 |
| --- | --- | --- | --- |
| **工作记忆**（上下文） | 当前几轮的推理、正在改的文件片段 | 窗口大小 | 压缩、截断、被噪声挤掉 |
| **外部状态**（文件系统 / git / 待办） | 目标、约束、已完成的步骤、待办清单 | 不受限 | 没人维护就过期 |
| **长期记忆**（知识页 / memory 文件） | 跨任务的约定、踩过的坑、项目结构 | 不受限 | 写入质量差就变成噪声 |

一条实用原则：必须记住的内容写到上下文之外，上下文里只留指针。一条"TODO: 修 store 的重复 key（见 notes.md#store）"只占十几个 token，比在上下文里复述三百字的需求可靠得多，因为它不会被压缩掉。

## 先规划，还是边走边改

> **先规划后执行**
> 先产出一份步骤清单（写进待办），再逐步执行。好处是过程可检查、可中断、可并行；坏处是需求模糊时，计划本身就是错的。
> 适合：任务边界清楚、步骤多、可拆分的活。

> **边做边想（ReAct）**
> 每步根据上一步的结果决定下一步。好处是能应对意外、能边探索边修正；坏处是容易跑偏、容易在局部最优里打转。
> 适合：探索型任务、信息不足、需要先摸清代码库。

实践里两者混着用：先用几步探索摸清地形，列一份待办，再按待办推进，遇到意外切回逐步探索。待办的意义不只是提醒模型别漏，还在于让用户和 harness 都能看到进行到哪一步。

## 常见的失败和对策

| 失败 | 表现 | 对策 |
| --- | --- | --- |
| 原地打转 | 反复读同一个文件、跑同一条命令 | 检测重复动作；把"已尝试过"写进待办 |
| 幻觉工具 | 调用不存在的工具或参数 | 白名单校验；错误信息里列出可用工具 |
| 过早收工 | 改了一半就说"已完成" | 强制跑验证（测试/构建）；定义"完成的判据" |
| 上下文腐烂 | 越往后越忘记最初的约束 | 把约束固定在系统提示或状态文件里 |
| 噪声淹没 | 被 5 万行日志淹没，抓不住关键的那一行报错 | 工具侧压缩；只回错误行与上下文各 3 行 |
| 越权操作 | 删库、改系统配置、提交密钥 | 权限分级 + 危险操作审批（第 21 章） |
| 范围漂移 | 顺手重构了三个无关文件 | 明确 in-scope；diff 审查；小步提交 |
| 成本失控 | 一步读进 200K 上下文 | 单步输入上限、总预算、超限即停 |
| 验证作弊 | 改测试让它通过，而不是改代码 | 测试文件只读；diff 检查是否动了断言 |
| 静默失败 | 命令报错被忽略，继续往下走 | 非零退出码必须显式处理 |

## 怎么评测一个 agent

单次调用只看答案，agent 还要看过程和花销：终态、轨迹、成本。

- **终态**：任务是否真的完成。真实仓库的 issue → patch 修复（SWE-bench 这类基准），或者终端里的多步操作（Terminal-Bench 这类）——判据都是"跑验证脚本通过"，而不是"模型说它完成了"。
- **轨迹**：用了几步、调了哪些工具、有没有越权、有没有重复动作。轨迹断言（tool 调用序列包含测试、没有修改断言文件）比终态更能发现"蒙对的"。
- **成本**：每任务 token 与耗时。两个成功率相同的方案，成本差 5 倍就是两个产品。

**成本算例（30 步、平均输入 20K、输出 500 token/步、缓存命中 85%）**

| 项 | 值 |
| --- | --- |
| 输入（未命中部分） | 600K × 15% = 9 万 token 按全价计 |
| 输入（命中部分） | 600K × 85% = 51 万 token，通常按 1/10 计价 |
| 输出 | 15K token，单价通常是最贵的 |
| 结论 | 命中率从 0 提到 85%，总成本大约降到 **1/4**——这就是 agent 必须做前缀稳定化设计的原因 |

## 该不该用 agent

| 四个问题 | 都答"是"才值得上 agent |
| --- | --- |
| 任务需要多次观察与修正吗？ | 一次调用能答好的事，套上 agent 只会更慢更贵更不稳 |
| 有可验证的中间信号吗？ | 没有测试、没有编译、没有对错判据时，agent 的"多步"只是在放大幻觉 |
| 工具足够可靠吗？ | 工具本身 50% 失败，agent 的成功率会被指数级压下去 |
| 出错可回滚吗？ | 不可逆的操作（删数据、发钱、对外发布）必须有人审或沙箱兜底 |

> **小结**
>
> agent 的能力来自步数乘以每一步的一次前向，这一点和思维链同源，区别在于它能拿到环境的真实反馈。工具调用并不是模型"会"用工具，而是声明、解析、执行三方按同一个格式配合，parser 配错是最常见的原因。限制和成本几乎都来自上下文：工具输出增长最快，所以压缩点（窗口的 70%–85%）比窗口大小更关键；钱主要花在"输入长度 × 步数"上，而前缀缓存能不能命中，决定了这笔钱能省下多少。先把前缀稳定下来，再谈其他优化。
